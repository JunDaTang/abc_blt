# ABC 作业成本法 — 物流成本分析系统

## 一句话说明

把一个快递公司每月花的钱，精确地算到每一个快递包裹上。

---

## 用例子理解 ABC

### 问题：100 万怎么分到每个包裹上？

假设你开了一家快递公司，某个月总共花了 **100 万元**，送了 **50 万个包裹**。

最简单的想法：每个包裹 2 元？但显然不公平——

- 同城件只用分拣+派送，成本应该低
- 跨省件还要长途运输，成本应该高
- 大客户一件 50kg，小客户一件 0.5kg，成本不可能一样

**ABC（作业成本法）的思路**：不是平均分，而是按"每个包裹实际消耗了什么"来分。

### 先搞清楚五个概念

在 ABC 里有五个关键概念，成本从上游一步步流向下游：

```
财务科目              资源                部门            作业            运单
（钱花在哪类东西上）  （哪个部门的哪类东西）（谁在用）      （干了什么活）  （谁享受了）

薪酬福利 30万   →   运输车辆(运输部)  →  运输部 50万  →  干线运输 45万  →  包裹A
燃油费   20万   →   分拣设备(分拣部)  →  分拣部 38万  →  分拣作业 30万  →  包裹B
办公租金 20万   →   管理支持(管理部)  →  管理部 12万  →  打包作业 20万  →  包裹C
...
```

注意"科目"和"资源"的区别：
- **科目**是财务视角：薪酬福利、燃油费、办公租金（会计记账用的）
- **资源**是部门视角：运输部的运输车辆、分拣部的分拣设备（部门实际占用的东西）

一个科目可能属于多个部门（比如燃油费，运输部和分拣部都在用），一个部门可能有多个资源。

---

### 四级分摊模型（代码的核心逻辑）

成本从财务科目流转到最终包裹，经过四步分摊。每一步都基于同一个例子，数字是连续的：

> **背景数据**
> - 3 个部门：运输部、分拣部、管理部
> - 3 个作业：干线运输、分拣作业、打包作业
> - 50 万个包裹

#### 第 0 步：资源归集 — 财务科目 → 部门资源池

在分摊之前，先把财务科目归集到各部门。

有些科目可以直接归属到某个部门（比如运输部专属的车辆折旧），有些是**共享科目**，先进入"共享资源池"，等第 1 步（RR）再分摊：

| 财务科目 | 金额 | 归属方式 | 运输部 | 分拣部 | 管理部 |
|---------|------|---------|--------|--------|--------|
| 薪酬福利 | 30万 | 直接归属 | 10万 | 8万 | 12万 |
| 车辆折旧 | 10万 | 直接归属 | 10万 | — | — |
| 设备折旧 | 10万 | 直接归属 | — | 10万 | — |
| **燃油费** | **20万** | **共享** | — | — | — |
| **办公租金** | **20万** | **共享** | — | — | — |
| **场地租金** | **10万** | **共享** | — | — | — |
| **直接归属小计** | **50万** | | **20万** | **18万** | **12万** |
| **共享资源池** | **50万** | | | | |
| **总计** | **100万** | | | | |

> 直接归属 50万 + 共享资源池 50万 = 100万。共享资源池（燃油、租金）将通过第 1 步 RR 分摊到运营部门。

---

#### 第 1 步：RR — 资源 → 资源（共享资源池分摊到各部门）

> **RR 解决什么问题？**
>
> 第 0 步中有 50 万共享资源池（燃油 20万 + 办公租金 20万 + 场地租金 10万），还没有归入任何部门。
> RR 的作用就是把这些共享资源，按动因分给各个部门。

> **场景**：代码中 RR 统一使用动因 **RR002 = 收派票数**（各运营网点处理的运单张数）作为分摊依据。
> 注意：管理部不直接处理运单，不参与 RR 分摊，其成本在 RA 阶段直接分配给作业。
> - 运输部网点处理了 60% 的运单
> - 分拣部网点处理了 40% 的运单

```
共享资源池 50万（对应代码动因 RR002：收派票数）
  ├── 运输部   30万  (60%，按收派票数)
  └── 分拣部   20万  (40%，按收派票数)
```

RR 分摊后，各部门资源池 = 直接归属 + RR 分入：

```
运输部：20万(直接) + 30万(RR) = 50万
分拣部：18万(直接) + 20万(RR) = 38万
管理部：12万(直接) + 0(RR不分) = 12万
合计：50 + 38 + 12 = 100万 ✓（成本守恒，100万全部归集到部门）
```

代码对应：`7.2-RR分摊程序.prc`，规则配置在 `ABC_REL_RR_DIST`

---

#### 第 2 步：RA — 资源 → 作业（每个部门的资源池分给各项作业）

> **RA 解决什么问题？**
>
> 现在每个部门都有一笔资源池了。但部门不是最终消耗者——**作业**才是。
> RA 把每个部门的资源池，按资源动因分给各项作业。

> **场景**：
> - 运输部 50 万 → 干线运输 40万，运输闲置容量 5万（辅助作业），城配 5万
> - 分拣部 38 万 → 分拣作业 22万，打包作业 16万
> - 管理部 12 万 → 分拣作业 8万，打包作业 4万（管理部不直接处理运单，成本在 RA 阶段直接分给作业）

```
运输部 50万                    分拣部 38万
  ├── 干线运输    40万             ├── 分拣作业  22万(58%)
  ├── 运输闲置容量 5万 ← 辅助作业   └── 打包作业  16万(42%)
  └── 城配         5万

管理部 12万（不处理运单，RA 直接分给作业）
  ├── 分拣作业    8万(67%)
  └── 打包作业    4万(33%)
```

RA 分摊后，各作业成本汇总：

```
干线运输：40万
分拣作业：22 + 8 = 30万
打包作业：16 + 4 = 20万
城配：5万
运输闲置容量：5万（辅助作业，待 AA 分摊）
合计：40 + 30 + 20 + 5 + 5 = 100万 ✓
```

代码对应：`7.2-RA分摊程序.prc`，规则配置在 `ABC_REL_RA_DIST`

---

#### 第 3 步：AA — 作业 → 作业（辅助作业之间的分摊）

> **AA 解决什么问题？**
>
> 有些作业是"辅助作业"——它不直接处理包裹，但帮了生产作业的忙。
> 在本项目中，AA 的核心场景是**运输闲置容量分析**（对应代码动因 AA002）。

> **场景**：RA 中识别出的"运输闲置容量"5 万（车辆未满载的浪费成本），按实际装载情况分摊回干线运输。
> 代码中把车辆载重（上限 3000kg）拆分为**正常装载**和**闲置容量**，用于量化空载浪费。

```
运输闲置容量 5万（辅助作业，对应代码 AA002：装载重量）
  └── 干线运输  5万  (100%，闲置成本归入运输总成本)
```

AA 后，各生产作业成本：

```
干线运输：40 + 5 = 45万（含闲置容量成本）
分拣作业：30万
打包作业：20万
城配：5万
合计：45 + 30 + 20 + 5 = 100万 ✓
```

> **AA 的业务价值**：把运输成本拆成"有效装载"和"闲置浪费"两部分，让管理层看到有多少成本花在了空载上，从而推动优化装载率。

代码对应：`7.2-AA分摊程序.prc`，规则配置在 `ABC_REL_AA_DIST`

---

#### 第 4 步：AO — 作业 → 运单（最终分到每个包裹）

> **AO 解决什么问题？**
>
> 现在每个作业都有了一笔总成本。最后一步是把作业成本分给每个包裹。
> 分配的依据是"动因量"——每个包裹在该作业上消耗了多少。

> **场景**：
> - 干线运输 45 万 ÷ 总运输重量 200 万公斤 = 每公斤 0.225 元（对应代码动因 AO005，按运单重量分摊，含闲置容量成本）
> - 分拣作业 30 万 ÷ 总分拣次数 40 万件 = 每件 0.75 元（对应代码动因 AO006/AO007，按装卸票数）
> - 打包作业 20 万 ÷ 总打包次数 25 万单 = 每单 0.8 元（对应代码动因 AO008/AO009，按中转票数）
> - 城配 5 万 ÷ 城配次数 20 万次 = 每次 0.25 元

```
干线运输 45万 ÷ 200万公斤 = 0.225元/公斤（按运单重量）
分拣作业 30万 ÷ 40万件 = 0.75元/件（按装卸票数）
打包作业 20万 ÷ 25万单 = 0.8元/单（按中转票数）
城配      5万 ÷ 20万次 = 0.25元/次

包裹A（跨省件，5公斤）：5公斤×0.225 + 2次分拣 + 1次打包
  = 1.125 + 0.75×2 + 0.8 = 3.425 ≈ 3.43 元

包裹B（同城件，3公斤）：0公斤干线 + 1次分拣 + 1次打包
  = 0 + 0.75 + 0.8 = 1.55 元
```

跨省件分摊 3.43 元，同城件分摊 1.55 元 —— 这就是 ABC 比"每个包裹 2 元平均分"更精确的地方。

代码对应：`8.2-AO分摊程序.prc`，规则配置在 `ABC_REL_AO_DIST`

### 全链路总结

```
财务科目 100万
  │
  ├─ 直接归属 ─────────────────────────────────┐
  │  薪酬30万 + 车辆折旧10万 + 设备折旧10万 = 50万 │
  │                                             │
  ├─ 共享资源池 ───────────────────────────────┐│
  │  燃油20万 + 租金20万 + 场地10万 = 50万     ││
  │     ↓                                       ││
  │  RR: 按收派票比分给各部门                   ││
  │     ↓                                       ││
  ├─────────────────────────────────────────────┘│
  │                                               │
  ▼                                               ▼
部门资源池: 运输部50万 / 分拣部38万 / 管理部12万 = 100万
  │
  │ RA: 按资源动因分给各作业
  │
  ▼
作业成本: 干线40万 / 分拣30万 / 打包20万 / 城配5万 / 运输闲置5万 = 100万
  │
  │ AA: 辅助作业(运输闲置容量)归入干线
  │
  ▼
生产作业: 干线45万 / 分拣30万 / 打包20万 / 城配5万 = 100万
  │
  │ AO: 按作业动因(重量/票数)分给每个包裹
  │
  ▼
运单成本: 跨省件3.43元 / 同城件1.55元
```

### 最终产出：每个包裹的成本明细

四步分摊完成后，每个包裹都有了成本明细，可以回答这些业务问题：

| 分析维度 | 问题示例 |
|---------|---------|
| **区部利润** | 北京区部这个月赚了多少？（收入 - 成本） |
| **流向利润** | 北京→上海这条线路赚钱吗？北京→广州呢？ |
| **客户利润** | 大客户 A 到底给公司贡献了多少利润？ |
| **产品利润** | 次日达和标准件，哪个更赚钱？ |
| **成本结构** | 我们的成本主要花在运输还是人工？ |

这些分析都在 `ABC_BSL_COST_BASE`（成本分析基表）上完成，对应 `9.1-分析脚本.sql` 和 `10.3-分析脚本.sql`。

## 代码执行顺序

先建表，再灌基础数据，再按顺序跑四级分摊，最后汇总分析：

```
3.x 建资源维度表       →  4.x 导入运单/机构/财务数据
        ↓
5.x 配置分摊规则       →  6.x 计算动因量
        ↓
7.x RR分摊  →  RA分摊  →  8.x AA分摊  →  AO分摊
                                            ↓
                                   10.x 汇总到成本基表
                                            ↓
                                      9.x 利润分析
```

## 按 OneData 接入公司数仓的改造方案

> 如果要将本项目接入公司数仓体系，以下是具体的改造方案。
> **原则：分摊计算逻辑不变，只改表名和分层。**

### 分层映射总览

```
改造前（当前）                        改造后（OneData）
─────────────────────────────────    ─────────────────────────────────
ODS_                                → ods_         （保持不变）
ABC_DIM_*                           → dwd_abc_dim_*（维度表归入 DWD）
4.x 业务基础表                       → dwd_abc_*    （明细数据归入 DWD）
ABC_REL_*                           → dwd_abc_rel_*（规则配置归入 DWD）
*_TMP*                              → dws_abc_*    （中间结果升级为 DWS）
ABC_BSL_COST_BASE                   → ads_abc_cost_base（产出归入 ADS）
```

### 第一步：ODS 层 — 保持不变

ODS 层本身就符合 OneData 规范，无需改动。

| 现有表名 | OneData 表名 | 说明 |
|---------|-------------|------|
| ODS_SUBJ_ACCO | ods_subj_acco | 科目余额接口表（已符合） |

### 第二步：DWD 层 — 明细数据 + 维度 + 规则配置

DWD 层包含三类数据：**维度表**、**业务明细表**、**规则配置表**。

#### 2.1 维度表

#### 2.2 业务明细表

| 现有表名 | OneData 表名 | 来源文件 | 说明 |
|---------|-------------|---------|------|

| ABC_REL_CUST | dwd_abc_cust | 4.3 | 客户信息 |

### 第三步：DWS 层 — 分摊中间结果（收益最大的一步）

把 TMP 临时表升级为 DWS 层持久化表，**这是改造收益最大的一步**：
- TMP 表每次跑完数据就丢了，排查问题无据可查
- 落为 DWS 后，可以按月回溯每一级分摊的中间结果

| 现有表名 | OneData 表名 | 说明 |

| ABC_FCT_RA_DRIV | dws_abc_ra_driv | RA 动因结果 |
| ABC_FCT_RA_DIST_TMP01~04 | dws_abc_ra_dist_tmp01~04 | RA 分摊中间过程 |
| ABC_FCT_RA_DIST | dws_abc_ra_dist | RA 分摊最终结果 |
| ABC_FCT_AA_DRIV | dws_abc_aa_driv | AA 动因结果 |
| ABC_FCT_AA_DIST_TMP01~04 | dws_abc_aa_dist_tmp01~04 | AA 分摊中间过程 |
| ABC_FCT_AA_DIST | dws_abc_aa_dist | AA 分摊最终结果 |
| ABC_FCT_AO_DRIV | dws_abc_ao_driv | AO 动因结果 |
| ABC_FCT_AO_DIST_TMP01~04 | dws_abc_ao_dist_tmp01~04 | AO 分摊中间过程 |

### 第四步：ADS 层 — 最终产出

| 现有表名 | OneData 表名 | 说明 |
|---------|-------------|------|
| ABC_BSL_COST_BASE | ads_abc_cost_base | 成本分析基表（最终产出） |

### 存储过程改造要点

表名改了之后，所有引用这些表的存储过程都要同步修改：

| 存储过程文件 | 需修改的内容 |
|------------|------------|
| `7.2-RR分摊程序.prc` | ABC_FCT_RR_DIST* → dws_abc_rr_dist*，ABC_FCT_RR_DRIV → dws_abc_rr_driv |
| `7.2-RA分摊程序.prc` | ABC_FCT_RA_DIST* → dws_abc_ra_dist*，ABC_FCT_RA_DRIV → dws_abc_ra_driv |
| `8.2-AA分摊程序.prc` | ABC_FCT_AA_DIST* → dws_abc_aa_dist*，ABC_FCT_AA_DRIV → dws_abc_aa_driv |
| `8.2-AO分摊程序.prc` | ABC_FCT_AO_DIST* → dws_abc_ao_dist*，ABC_FCT_AO_DRIV → dws_abc_ao_driv |
| `8.2-生成AO动因.prc` | ABC_FCT_AO_DRIV → dws_abc_ao_driv |
| `10.2-成本分析基表数据程序.prc` | ABC_FCT_AO_DIST → dws_abc_ao_dist，ABC_BSL_COST_BASE → ads_abc_cost_base |
| `9.1-分析脚本.sql` | ABC_FCT_AO_DIST → dws_abc_ao_dist，ABC_BSL_WAYBILL → dwd_abc_waybill |
| `10.3-分析脚本.sql` | ABC_BSL_COST_BASE → ads_abc_cost_base |

> **注意**：PL/SQL 存储过程中表名是硬编码的，没有编译器帮你检查。建议每个存储过程改完后，用 `grep` 确认旧表名已全部替换。

### 改造优先级建议

| 优先级 | 动作 | 原因 |
|-------|------|------|
| **P0** | TMP 表落为 DWS | 收益最大：可回溯、可排查、可复用 |
| **P1** | 产出表改 ADS | 与下游系统对接时命名统一 |
| **P2** | 维度表改 DIM 前缀 | 与其他数仓项目的维度表统一规范 |
| **P3** | 规则配置表改 DWD | 最后做，因为规则表改动不影响计算逻辑 |
| **不做** | ODS 层保持不变 | 已经符合规范 |
